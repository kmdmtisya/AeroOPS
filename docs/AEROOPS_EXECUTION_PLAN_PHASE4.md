### Step 4.1 — Simulated partner feed adapter (stands in for backlog F07's "connect a feed") ✅ DONE

**Goal:** a background job that periodically emits synthetic flight-update events through the real ingestion path, so later steps (dashboard, staleness banners) have live-changing data without a human posting curl requests by hand.

- [x] **`SimulatedFeedProperties`** — new `com.aeroops.feed` package, `@ConfigurationProperties(prefix = "aeroops.simulated-feed")`: `enabled` (boolean, default `false`), `tenantId` (default `demo-airport`), `source` (default `SIMULATED_AOCC`). Registered via `@EnableConfigurationProperties` on `ApiApplication` rather than a component-scanned bean, matching the fact that no other `@ConfigurationProperties` class existed yet in this codebase (first introduction). — ✅ _Completed: 2026-09-30_
- [x] **`SimulatedFeedScheduler`** — `@Component`, `@Scheduled(fixedDelayString = "${aeroops.simulated-feed.poll-interval-ms:15000}")` `tick()` method, guarded by `properties.isEnabled()`. Binds `TenantContext`/`ActorContext` (`"simulated-feed"`) in a try/finally exactly as `TenantFilter` does for real requests — necessary because a `@Scheduled` method runs on a thread with no JWT/filter chain to populate either `ThreadLocal`. Maintains a small rotating pool of 3 synthetic flights (`SIM-FEED-2001/2002/2003`, source `SIMULATED_AOCC`) and, on each tick, advances one of them one step through the lifecycle (`SCHEDULED → INBOUND → ON_BLOCK → TURNAROUND → READY → OFF_BLOCK`, wrapping around), builds a real `InboundEventEnvelopeRequest` with a fresh UUID `event_id`, and calls `IngestionService.ingest(...)` directly in-process — the same convention `IngestionServiceTest`/`Phase3ExitGateTest` already use for direct-service-call tests, and matches the Explore-confirmed fact that ingestion has no HTTP-only entry point requirement. `ingestNextStep()` is exposed package-visible as the deterministic, schedule-free seam for tests. — ✅ _Completed: 2026-09-30_
- [x] **Wire `@EnableScheduling`** — added to `ApiApplication` alongside `@EnableConfigurationProperties(SimulatedFeedProperties.class)`. No new Maven dependency needed (`spring-boot-starter-web` already pulls `spring-context`). — ✅ _Completed: 2026-09-30_
- [x] **Dev-profile config** — `application.yml`'s existing `dev` profile block gained `aeroops.simulated-feed.{enabled: true, tenant-id: demo-airport, source: SIMULATED_AOCC, poll-interval-ms: 15000}`. Not enabled outside the `dev` profile (default `enabled: false` in the properties class itself, belt-and-suspenders with the profile-scoped override). — ✅ _Completed: 2026-09-30_

### Step 4.2 — Role-aware authorization ✅ DONE

**Goal:** stop "any authenticated tenant user can call any endpoint." Before this step, `SecurityConfig` had zero `@PreAuthorize`/`hasRole` usage and no `JwtAuthenticationConverter` — confirmed by exploration before this plan was written — despite `viewer/handler/controller/planner/tenant-admin/auditor` already existing as realm roles in `infra/keycloak/realm-export.json`, assigned only to the single existing demo user (`demo.controller`).

- [x] **`RealmRoleConverter` + `JwtAuthenticationConverter` bean** in `SecurityConfig` — new `com.aeroops.config.RealmRoleConverter` (`Converter<Jwt, Collection<GrantedAuthority>>`) reads the JWT's `realm_access.roles` claim and maps each role to a `ROLE_...`-prefixed `GrantedAuthority` (uppercase, hyphen→underscore, e.g. `tenant-admin` → `ROLE_TENANT_ADMIN`). Wired into a `JwtAuthenticationConverter` via `setJwtGrantedAuthoritiesConverter(...)`, passed to `.oauth2ResourceServer(oauth2 -> oauth2.jwt(jwt -> jwt.jwtAuthenticationConverter(...)))`, replacing the previous no-op `.jwt(jwt -> {})`. First introduction of a custom role converter in this codebase. — ✅ _Completed: 2026-09-30_
- [x] **`@EnableMethodSecurity`** added to `SecurityConfig` to enable `@PreAuthorize`. — ✅ _Completed: 2026-09-30_
- [x] **Role mapping** — re-checked `AEROOPS_SYSTEM_DESIGN.md` and `AEROOPS_PRODUCT_BRIEF.md`; neither defines an explicit role/permission matrix beyond listing the six role names, so this step documents the default actually applied: `viewer`/`auditor` read-only everywhere (no restriction beyond authentication); `handler` may complete turnaround tasks; `controller`/`planner` may assign stands and manage incidents; `tenant-admin` does everything within tenant. Applied as `@PreAuthorize("hasAnyRole('CONTROLLER', 'PLANNER', 'TENANT_ADMIN')")` on `IncidentController.create/assign/resolve`, `StandAssignmentController.assign`, and `TurnaroundController.create`; `TurnaroundController.complete` additionally allows `HANDLER`. `FlightController`'s `GET`s and `IngestController` (machine-to-machine) left unrestricted as planned. — ✅ _Completed: 2026-09-30_

- [x] **Authorization tests** — new `RealmRoleConverterTest` (plain unit test: role-mapping correctness, empty result on missing `realm_access`) and new `IncidentAuthorizationTest` (`@SpringBootTest` + `@AutoConfigureMockMvc`, first MockMvc usage in this codebase, using spring-security-test's `jwt()` request post-processor with explicit authorities): proves a `viewer`-role token gets `403` on `POST /v1/incidents` and `200` on `GET /v1/incidents`, while a `controller`-role token gets `201` on the same `POST`. — ✅ _Completed: 2026-09-30_

## Sequencing and dependencies

**4.1 → 4.2 → 4.3 → 4.4.** 4.1 has no dependency on the others and is done. 4.2 depends only on the existing tenant/security foundation and is done. 4.3 depends on 4.2 for role-aware UI and reads the data 4.1 produces, and is done at the API-verification level (browser walkthrough folded into 4.4, see 4.3's live-verify note). 4.4 ties 4.1–4.3 together into `Phase4ExitGateTest` and a live-verify pass, and is itself done at the same API/source-level of verification — the browser-visual half (staleness banner rendering, buttons appearing/disappearing on screen) was not performed by this plan, for the same reason as 4.3: no browser-automation tool is available in this environment. With 4.1–4.4 all complete, the *engineering* half of Phase 4's exit gate (Gate G2 — integrated staging environment, here the local Compose stack standing in for it) is met; the external-security-review half of Gate G2 is explicitly **not** claimed as done.

## What this plan deliberately does not cover

Per the roadmap, mobile web task-update screens for ramp agents (Phase 4 step 3) are skipped — no mobile-specific need has been identified yet, and the desktop dashboard covers the pilot use case being built here. Real alert routing/notifications (Phase 4 step 4) are skipped — that needs a real channel (email/SMS) and a business decision about who gets paged. An actual external security review (Phase 4 step 7, half of Gate G2) is **not** performed by this plan and cannot be — it requires a human reviewer, not code; Step 4.4 explicitly does not claim it as satisfied. Load/security testing at pilot scale (Phase 5) is out of scope here, as is the rule-based risk scoring and optional copilot (also Phase 5) — each has its own phase and gate.
