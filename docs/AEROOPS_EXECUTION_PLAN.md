### Step 3.2 — Flight canonical view updates (backlog F03) ✅ DONE

Deliverables:
- Extend `FlightController`/`FlightLegRepository` so ingestion (3.1) actually mutates `FlightLeg` rows: on an accepted `flight.update` event, upsert by `(tenant_id, source_system, external_id)` (the existing `uq_flight_leg_source_identity` constraint), update whichever of scheduled/estimated/actual timestamps and `lifecycle` the event carries, bump `updated_at`.
- Source-lineage rule: if two sources disagree, the later `occurred_at` for the *same field* wins, but never overwrite a field the incoming event leaves null — this is what "source of truth stays explicit" (roadmap cross-cutting rule) means concretely here.
- `FlightView` already exposes scheduled/estimated/actual separately (done in Phase 2) — no DTO change needed, just confirm ingestion writes populate it correctly.
- Test: ingest a `flight.update` for `SIM-FL-1001` with a new `actualOffBlock`, confirm `GET /v1/flights/{id}` reflects it and `updatedAt` advances; confirm a second event with an older `occurred_at` for the same field does not regress it.

**Verification evidence:** covered by the same `IngestionServiceTest` run as 3.1 — `laterEvent_updatesLifecycleAndActualTime_withoutRegressingUntouchedFields` and `outOfOrderEvent_isIgnored_andDoesNotRegressAlreadyAppliedState` exercise exactly this. `FlightLeg.applyUpdate()` implements the never-overwrite-with-null / later-`occurred_at`-wins rule via the new `last_event_occurred_at` column (added in `V3`).

## Sequencing and dependencies

Steps 3.1 → 3.2 are strictly ordered (ingestion must exist before it can drive canonical-view mutation). 3.3 and 3.4 both depend on 3.2 (need a real `FlightLeg` to attach to) but are independent of each other and can be done in either order or in parallel. 3.5 depends on nothing but the existing tenant/audit foundation and can start any time — it's the smallest, lowest-risk step and a reasonable one to do first if you want an early win. 3.6 depends on all of 3.1–3.4 (it doesn't require 3.5).

Suggested order for a single engineer working sequentially: **3.1 → 3.2 → 3.5 (quick win) → 3.3 → 3.4 → 3.6.**

## What this plan deliberately does not cover

Per the roadmap, Phase 4+ items (real feed adapter, AOCC dashboard, mobile task-update screens, alerting, rule-based risk scoring, the optional copilot, load/security testing, shadow pilot) are out of scope here — each has its own phase and gate and shouldn't be pulled forward the way Phase 2 was, since they depend on either Phase 3 being real first or on business decisions (G1/G2) that haven't happened.
